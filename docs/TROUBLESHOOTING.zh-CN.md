这是 `litearm` C++ SDK 的排查指南，它通过串口线协议驱动 7 轴机械臂——当 `connect()`、
`enable()` 或某条运动命令失败、行为异常，或返回你无法解释的结果时读它，按现象 → 原因
→ 处理往下走。

# litearm-cpp 现场排查手册

每条都遵循同样的三段式：**现象 → 原因 → 处理**。先看下面的速查表。

建议排查顺序：先看**错误码**（§4 提醒两个容易混淆的错误码空间），再看**链路诊断计数**
（§11），最后才怀疑线缆。

> 本文件是上游 `litearm-python/TROUBLESHOOTING.md` 的 C++ 版本。现象和原因是**固件
> 行为**，与语言无关；这里的入口名已改写为 C++ API（例如 `arm.model().commit()`）。
> **注意：** 上游文档最后一节里的“尚未验证”项，在本次移植中**同样未验证**——不要因为
> 语言变了就以为它们已经验证过。见 §16。

## 1. `connect()` 连不上

**现象**：`TransportError`（打不开端口 / 找不到设备）或 `FirmwareMismatchError`
（版本不匹配）。

| 原因 | 如何确认 |
| --- | --- |
| 找不到设备——没插、没驱动、不是 `1d50:606f` | `lsusb`；单独调用 `litearm::find_cdc_port()` 看它返回什么 |
| 端口已被占用——另一个进程或会话还开着它 | Linux 上 `fuser /dev/ttyACM0`；Windows 由系统强制独占，拿不到就打不开 |
| 固件太旧（< 1.5.0），或版本串不符合约定 | 读 `FirmwareMismatchError` 的消息——它引用了**实际看到的**版本串 |

**处理**：`FirmwareMismatchError` 就烧 `Litearm1.5.0` 或更新版本；端口被占用就关掉占用它的进程。

**注意：** 设备**重新枚举**（拔插、`enter_dfu()` 之后、真正断电重启）会改变
`/dev/ttyACM*` 的**编号**。把 `LITEARM_PORT` 写死的脚本现在指向一个不存在的端口——这是
“刚才还好好的”最常见的原因。

**注意：** 本库**不读任何环境变量**：`LITEARM_PORT` 只是 `env.sh` / 示例层使用的东西。

## 2. `enable()` 被拒

**现象**：`enable(attempts)` 抛出 `CommandRejectedError`。

**原因与处理**：`attempts` 只重试**白名单**里的码——只有下面标记“可重试”的那个会重发。
其它码重发**完全没用**，只会浪费时间。

| 码 | 含义 | 处理 |
| --- | --- | --- |
| `ERR{0x10,0x03}` | 瞬时失败（固件白名单里唯一可重试的） | 交给 `attempts`，或稍后重发 |
| `ERR{0x10,0x06}` | **锁存**故障——重发无用 | 先 `reset()`，再查是哪一轴（`st->joint_fault` / `st->fault_axes()`） |
| `ERR{0x10,0x07}` | 重发无用 | 查固件码表 |
| `ERR{0x10,0x00}` | **固件没有这条命令** | 固件太旧，升级 |

**注意：** 这里经常混进一个近亲：**臂未使能时，`movej` 会被 `ERR[01,3]` 拒绝**，而它的
消息同时指向**两种**可能——“未使能**或** EMERGENCY 锁存”。别只读前半句。

## 3. fork 出来的子进程行为异常

**原因**：`fork` **不复制线程**，但**会复制文件描述符**。所以子进程里的命令**真的会发到线上**，
而父进程的读线程会吃掉应答。见 [README](../README.md) 的多进程一节。

**如何识别**：

| 现象 | 解释 |
| --- | --- |
| 命令“超时”，但重试“有时能成” | 命令**确实发出去了**；父进程读走了应答 ⇒ 那次重试是**重复下发** |
| `get_state()` 不报错，但数值**从不变化** | 它静默返回继承来的**陈旧**值——最隐蔽的一种 |
| 子进程里 `connect()` 抛异常 | 父进程还占着端口 ⇒ 父进程必须先 `close()` |
| 任何命令立刻抛 `ForkedSessionError` | 守卫**工作正常**；这不是故障 |

**处理**：让父进程先 `close()` 释放端口，再 `fork`，然后在子进程里**新建** `Arm`。

**注意：** C++ 里还多一层：子进程中的 `close()` **故意泄漏**两个句柄（`Ack` 和传输层）——
销毁它们会永久挂起（见 README 那一节）。这个泄漏是有界且刻意的。

## 4. 两个容易混淆的错误码

### `ERR{0x02,0x03}` 是二义码

**同一个 `(命令, 码)` 二元组在固件里有两个完全不同的来源**：它既表示“未使能 / EMERGENCY
锁存”，也表示“IK 不可达 / 解非法”。

**处理**：收到它**不代表**臂已经失能。看**当前状态**（`st->enabled()` / `st->mode`），
而不是看码——如果臂是使能的，你就在 IK 那一支上。

### 两个都取 1–6 的码空间

| 来源 | 含义 |
| --- | --- |
| `0x4E` 应答里的 `err` 字段（`CartPlan::err`） | **规划结果本身**：不可达 / 共线 / 超容量 / 越限 |
| `RSP_ERR` 的第二个字节 | **门禁原因码**：未使能 `0x03` / 拖动示教中 `0x04` / `drop_hold` `0x06` |

**两者都取 1–6，但含义毫无关系。** 拿到一个“3”时，先问它来自哪条路径。

## 5. 连续笛卡尔命令会丢应答

**现象**：连续下发几条 `move_l` / `move_path` 后，其中一条抛 `CartReplyLostError`
（“结局未知”），或后续应答**错位**（一条命令的答案被下一条收走）。真机上 3/3 次复现。

**原因**：固件一次只保留**一个**待规划槽位——它不是队列。被取代命令的取消应答会互相
覆盖，所以少一条应答就会让整个配对序列错位。**根因在固件，不在本库。**

**处理**：笛卡尔命令**串行**下发——等一条结束再发下一条。库在**单进程内**已经串行化调用，
所以正常使用不会撞上；只有跨进程或多客户端并发才会。

## 6. `move_c()` 圆弧失败

**现象**：抛出 `CartesianPlanError`，臂**完全不动**。

| `err` | 原因 |
| --- | --- |
| `2` | **三点共线**（或接近共线）——圆心跑到无穷远 |
| `1` | 无 IK 解。从**完全伸展的 `home` 位姿**（奇异构型）出发**总是**这样；固件做得对，不是缺陷 |
| `3` | 超容量 / 不可达 |

**处理**：选三个不共线的点；从奇异构型出发时，先离开奇异构型。

**注意：** `move_c(start, via, goal)` 里的 **`start` 必须与调用时的实测 TCP 一致**
（容差 6 mm / 0.03 rad）。它不是自由的“从这里开始”参数——它会**和现实对账**，所以拿运动
中途的 TCP 当起点会被拒。**注意：** **`via` 的姿态被忽略**；只有它的位置参与定义圆。

## 7. 笛卡尔精度不是一个数

**末端残差取决于 [距离 × 速度 × 负载位姿]**。它不是某个固定的设备指标，并且会随负载明显变化。

**处理**：任何精度对比都必须使用**同一位姿、同一套约定、同一负载**——否则你测到的是位姿差
或负载差，不是精度差。

---

## 8. 恒定笛卡尔偏移——先查 `payload_mass`

**现象**：笛卡尔位姿带一个约 8 mm 的恒定偏移，与协议和规划器无关。

**原因**：设备里还留着过期的 `payload_mass = 1.0`（出厂默认应为 `0.0`）。固件的动力学补偿
使用这个质量，于是工具系被系统性地推偏。

**处理**：更换负载后**总是**调用 `set_payload()`。看到无法解释的恒定偏移时，先用
`get_ff_scalar(4)` 读回 `payload_mass`，然后再怀疑别的。

---

## 9. `movej` 在臂完全停稳前返回

**现象**：`movej` 返回的那一刻读状态，每个轴都还有一点残差。

**原因**：`movej` 在满足**到位判据**时返回——每个轴都在 `q_tol` 内，且速度连续 `arrive_frames`
帧都很安静。那一刻臂还没有完全停住。

实测（把 J6 驱动到 0.7）：返回瞬间读到 **0.6884**；5 秒内它自己收敛到 **0.6991**，并在那里
保持 20 秒。约 0.012 rad（0.7 度），在 `q_tol = 0.03` 内——**这是设计行为，不是漂移**。

**处理**：需要精确值时，等几秒再读，或自己收紧 `q_tol`。

## 10. `last_reset_reason()` 返回空串

**这是正确行为，不是解析失败。** 开机签名**只发一次**，而且只在**真正的 MCU 复位**之后，
`reset()` 不会让它重发。日常使用中拿到空串是预期的。

只有在你**在真正复位后很快连上**时它才有值（`"normal"` / `"iwdg-rst"`）。

**注意**，一个相关澄清：**`reset()` 是软件状态复位，不是 MCU 重启。** 它**不会**触发 USB
重新枚举，**同一个 `Arm` 对象之后仍可用**，签名也不会重发。

## 11. `kin_bench` 计数全为 0

**现象**：`arm.diag().kin_bench()` 的链路诊断计数（`crc_errors()` / `reply_dropped()` /
`can_tx_fail()` …）全读 0。

**原因**：这**不一定**表示链路干净。全 0 也可能表示“从来没读到过”——而这种失败是**静默的**：
不报错，只有一个看起来完全健康的 0。

**处理**：把它当链路健康检查之前，先确认帧真的在到达——看 `Msg.hz` / `Msg.timestamp`。
如果两者都是 `0.0`，那类帧**从未到达**。

**注意：** 这些计数里，`crc` 是实时且准确的；`can_tx_fail` 可能大得惊人（固件上报的累计值，
其确切定义尚未验证）。

## 12. `zero_g` 保活周期与异步退出

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 拖动示教期间运动命令被拒 | 固件看门狗语义：只有查询能通过 | 查询不受影响；**急停 / 失能是例外**，永远放行 |
| `period=0.5` 被本地拒绝 | 保活必须**小于 0.10 s**；固件 0.10 s 内收不到重发就掉进 fail-soft | 用 `[0.005, 0.10)` 内的 `period`；默认 `0.04` 没问题 |
| `zero_g_stop()` 之后立刻发运动命令被拒 | **退出是异步的**——调用返回后固件还需要一点时间收尾 | 稍等片刻再发运动命令 |

后台线程会自动重发保活。如果它因**写失败**停下，退出时会**抛出**，不会静默失败。可以通过
只读的 `zero_g_active()` / `zero_g_error()` 查看状态。

## 13. `move_js` / `send_mit` 之后臂慢慢变软

**原因**：这些是**连续伺服 / 透传**入口，**绕过运动规划**，而且**保活是调用方的事**：
**以 >=10 Hz 重发**。0.1 s 看门狗到期后，固件进入 fail-soft（降低刚度 + τ=0），臂在重力下
慢慢下沉——实测下沉量与“0.6× 刚度 + τ=0”的估计一致。

**处理**：只要还需要这个运动，就保持 >=10 Hz 重发。

**注意：** 数组长度必须是 **`n`**（本地检查），数值必须**有限**——`NaN` / `Inf` 会让固件拒绝
整帧（`ERR{cmd,0x02}`）。`send_mit` / `send_mit_all` / `move_js` 都有这个检查。
**注意：** `move_js` 里的 `dq` 是**速度参考**，不是钳制。

---

## 14. `enter_dfu()` 之后

- **不能立刻烧录**：`ACK{0x15}` 只表示“已登记”；设备必须先**重新枚举**成 `0483:DF11`。
  立刻烧录会失败；等十几秒再试就行。
- 判断设备是否真的走了，要看**读或写抛异常**——**不是** `is_open()`，也**不是**“读到 0 字节”。
- 一旦它成功返回，**这个 `Arm` 就死了**：所有入口都抛 `ArmIsInDfuError`（`close()` 除外）。
  烧完固件后**新建一个 `Arm`**。
- 使能中调用它会被**本地拒绝**（跳转会停 TIM3 ⇒ 电机 100 ms 内松开，有负载会下垂）。

---

## 15. 两个反直觉的参数行为

**`set_speed(percent)` 接受整数百分比，不是倍率。** `set_speed(1)` 表示**1% 速度**——按 0..1
的思维调用会得到一台爬行的臂。它还是**全局且持续**的（直到某个带复位语义的调用），这与
`movej(speed=0..1)` 的**单条轨迹倍率**不是一回事。参数必须是 **0..100 的 `int`**；越界值
本地拒绝（C++ 参数是 `int`，所以“传 bool”这类问题在这里不会出现）。

**`set_joint_limits()` 不是幂等的。** 固件**只允许收窄**，所以把**当前**值原样写回会被判成
“放宽请求”并拒绝（`ERR[23,2]`）。⇒ 不要拿它做“读—改—写”往返检查。

- **`capture()` 在失能时是否总是记录 0 帧**——这只出现在本仓的现场记录里；代码里没有对应

- **Windows**——未验证（串口后端已实现，但从未在真实 Windows 机器上运行）；
- **C++ 移植本身**：所有测试都是**离线**的（假传输 + 真实 pty），**没有一项在真机上跑过**——
  这与上面的条目是两回事，但也别假设它已经验证。

### 不可逆命令：不要在有标定的臂上运行

下面四条都会**覆盖或擦除本机单独辨识的动力学模型**，而且**没有撤销**：

| 命令 | 入口 |
| --- | --- |
| `0x25` | `arm.save_params()` |
| `0x32` | `arm.model().commit()` |
| `0x36` | `arm.params().reset_factory()` |
| `0x37` | `arm.model().revert()` |

**唯一安全的做法：在一块标定没有价值的板子上做。**

**注意**，还有：`0x33` `arm.model().set_jm()` **永远不该被调用**——它会重写关节映射
（包括符号），一次错误就让臂**乱摆**，而本地仅有的两条恢复路径（`revert` /
`save_params`）都在上面的表里 ⇒ **没有可靠的回退办法**。

**注意：** 压测 CAN 链路时只跑 **`candump`（只读）——绝不 `cangen`**：`can0` **就是**
电机总线。

## 17. 断电后 `enable()` 返回 `ERR{0x10,0x06}`（锁存）

**现象**（2026-09-28 真机实测，两次）：板子断电 ⇒ 臂失力、在重力下塌落 ⇒ 恢复供电后
`enable()` 返回 `ERR{0x10,0x06}`（锁存；必须先 `reset()`，**重发无用**）。

**注意：** **先分清是哪一种**——两次测量**形态不同，处理也不同**：

### 情况 A：全轴锁存（最常见）

```text
joint_fault=0x007F  enabled=0  err=0 (7/7 axes)  max torque amplitude ≈ 0.2 N·m (that is just noise)  FB_STALE
```

**这是“电机还没使能”的正常状态**，不是硬件坏了。按下面的顺序，实测恢复了：

```text
clear_faults()  ->  joint_fault cleared (0x007F -> 0x0000)
                   Warning: faulted() is still 1 here — because mode=EMERGENCY also counts as faulted
reset()         -> everything else cleared (flags zeroed, mode=INIT)
enable()        -> succeeds; and **the motors start reporting immediately** (axes with err=0: 7/7 -> 0/7)
```

⇒ 判据是**`enable()` 之后 `err` 是否变成 1**。如果变了，臂就是真的好了。

### 情况 B：单轴锁存

```text
joint_fault=0x0008 (axis 4)  FAULT + WD_TRIPPED + FB_STALE
enable() returns ERR{0x10,0x06}; movej() returns ERR{0x01,0x06} "rigid hold on lost link (drop_hold)"
```

实测：`clear_faults()` **逐位都没有变化**；`reset()` 能清掉，**但一个检查周期内又锁上**。

**注意：** **情况 A 和 B 的差异尚未解释**（怀疑是 `drop_hold` 与普通 `joint_fault` 不是
同一位，或与“那次 `enable()` 从未成功、电机从未上线”有关）。**本手册不为它们编造统一
理论**——两种情况都是实测，按实测写。

### 通用抓手

| 抓手 | 用法 |
| --- | --- |
| `joint_fault` 位图 | `0x0008` = bit3 = **4 轴**（1 基）。不需要拆整套——去查那一台电机 |
| `fault_axes()` | 同上，返回轴号列表 |
| **`err` 字节** | 看起来像“该轴电机**是否在报数**”：健康 = 1，总线断 / 未使能 = 0。注意：SDK 只**原样透传**、不解释，所以把它当**线索**，不要当结论 |
| `FB_STALE` 是“当前”还是“历史” | 调用一次 `reset()` 后立刻再读：**又出现** ⇒ 硬件仍有问题；**不再出现** ⇒ 只是历史锁存 |

### 两个容易误判的点

- **`enabled=1` 不等于“使能成功”。** 当固件与某台电机失联时，它会**给该轴自身加电托住**
  （“rigid hold on lost link”）。好处是臂不会掉；坏处是它**掩盖了“使能其实被拒”**这件事。
- **`reset()` 会掉使能**（实测 `enabled: 1→0`）。它是**软件状态复位，不是 MCU 重启**
  （见 §10）：不会触发 USB 重新枚举，同一个 `Arm` 对象之后仍可用。
